### Ce que vous demandez, et comment l'éviter en double

| Votre liste | Existe ? | Prévu | Se ferme quand |
| --- | --- | --- | --- |
| Intervention terminée **+** à valider | non | **une seule** action « à valider » (pas deux notifications pour le même fait) → planification + admin | l'intervention est validée |
| Facture à préparer | non | action → back-office | une finale active existe |
| Facture impayée | non | action après échéance → back-office ; escalade admin | payée ou annulée |
| Acompte impayé | **en partie** — encart à l'écran de Planification, pas de notification | action → back-office | payé |
| Contrat de sous-traitance signé | **non** (rien dans `lib/docusign`) | information → planification | — |
| Action attendue de la planificatrice | **en partie** — `quote.signed` l'avertit déjà à la signature | action « à planifier » **sans** nouvelle notification (elle existe déjà) | le dossier est planifié |
| Anomalie pour le Super Admin | non | action → admin : émission bloquée (identité légale), action back-office non traitée depuis N jours, cron muet | la cause disparaît |

**Le principe** : une action naît d'un **état** (dossier `finalise`, facture
échue…) et ne se ferme que lorsque cet état change. La notification n'est
qu'un **signal à la naissance** ; la lire ne ferme rien. Une **clé unique** par
action (« dossier X à valider ») interdit les doublons, même si le cron passe
deux fois.

**Architecture prévue** : une table d'actions back-office et une 4ᵉ passe
isolée du cron, réconciliée depuis l'état des dossiers et des factures — même
idempotence que le moteur commercial, sans le déformer. **Non développé** :
j'attends votre validation de ce tableau, et du délai d'escalade vers le
Super Admin.
